# ADR-0004: 項目には、そのソフトが最後に動いた日を Last sighted として載せる

- 状態: 採用

## 文脈

ADR-0003 で、項目に「書いてあることを確かめた日」を載せる欄を設けた。けれども、今すべての項目を確かめると、どの項目の日付も同じ日になる。日付どうしに差が生まれるのは何か月も先のことで、それまでのあいだ、読者が項目を比べる手がかりにならない。

読者が知りたいのは、そのソフトが今も手入れされているかどうかである。ほとんどの項目には GitHub のリポジトリへのリンクがあり、その既定ブランチの最新コミットの日付は機械的に取れる。この日付は項目ごとにばらつき、今の時点から読者の判断材料になる。

リンクが生きているかどうかは、リンク検査がすでに毎回確かめている。

## 決定

- 項目の日付の欄は Last sighted（キーは `lastsighted`）とする。値は、その項目の Sightings のうち、ラベルが「GitHub repository」のリンク先にある既定ブランチの最新コミットの日付とする。
- 「GitHub repository」のリンクがない項目には、Last sighted を載せない。
- 日付は `scripts/sightings.sh` が GitHub API から取って front matter に書く。項目を見直すときや版を改めるときに、人がこれを走らせる。日付は、その版の時点で最後に目撃された日を表す。
- GitHub Actions の `sightings` ワークフローは、手動で起動したときだけこのスクリプトを走らせ、日付が変わったときだけ PR を作る。その PR では、ビルド検査とリンク検査を `workflow_dispatch` で起動する。Actions の標準のトークンで作った PR では、`pull_request` のワークフローが動かないためである。
- WIP の表示は、日付とは切り離す。全項目の内容と種別を見直したときに外す。

## 理由

- 最新コミットの日付は、項目ごとに違う値を今すぐ示せる。
- 日付の取得は機械的にできるので、版を改めるたびに手間なく揃えられる。
- 図鑑は版を重ねるもので、版と版のあいだに書き換わらない。日付も版を改めるときにだけ動く。
- 標準のトークンだけで動くので、リポジトリに秘密情報を置かない（ADR-0001）。

## 採らなかった案

- 人が内容を確かめた日を載せる：今は全項目が同じ日付になり、読者の手がかりにならない。
- Wayback Machine のスナップショットの日付を載せる：スナップショットがあることは、誰かが中身を確かめたことを示さない。
- ビルドのたびに Hugo から GitHub API を呼ぶ：認証なしでは 1 時間に 60 回までで、ビルドが重なると足りなくなる。
- 最新リリースの日付を載せる：リリースを作らないリポジトリが多く、リリース後のコミットも活動の印である。
- 週に一度、日付を自動で更新する：活発なソフトの日付は更新のたびに直近に寄るだけで、毎週の差は読者の手がかりにならない。版と版のあいだに書き換わる図鑑の見立てにも合わず、毎週の PR をマージする手間も生む。

## 結果

- Xcode や Colaboratory のように、「GitHub repository」のリンクを持たない項目には日付が出ない。
- 日付は版を改めるまで古いままになる。止まったソフトと動いているソフトの区別は保たれる。
